1. Executive Summary

A full audit of the Cyoda TMS codebase — spanning the Spring Boot backend, React/TypeScript frontend, and the Cyoda gRPC data layer — identified seven distinct performance bottlenecks that compound each other at runtime. The two most damaging issues are architectural in nature:

  1. Every filtered database query performs a full-table scan across all projects and entities, then discards results in Java heap memory. As data grows, this degrades from linear to catastrophic.
  2. The frontend triggers an API waterfall (suites → cases per suite → steps per case) that must complete before the page becomes interactive, serializing what should be parallel work.
🔴 Critical Finding A project with 10 suites and 50 test cases per suite causes GET /projects/{id}/suites/{id}/cases to fetch and deserialize all test cases in the entire system — potentially thousands of records — for every single page load, discarding ~99% of them in memory.

The sections below present each finding with the exact offending code, an explanation of the performance impact, and specific, actionable remediation steps. The final section provides a prioritized roadmap distinguishing quick wins from longer-term architectural improvements.

2. Detailed Findings

1

Full-Table Scan on Every Filtered API Request

Critical  Backend

Affected files: TestCaseService.java, SuiteService.java, TestRunService.java, AttachmentService.java

Every service that needs to fetch a filtered subset of entities (e.g., "test cases for suite X") calls entityService.findAll() with a large pageSize=1000, retrieves all entities of that type from the Cyoda platform, deserializes them all into Java objects, and then filters them in a Java .stream().filter() pipeline in memory. This is equivalent to running SELECT * FROM test_cases and applying a WHERE suiteId = ? filter in application code rather than in the data layer.

Offending Code — TestCaseService.java

// ❌ PROBLEM: fetchs ALL test cases across ALL projects/suites
public PageResult<TestCaseDTO> getTestCasesBySuiteId(UUID suiteId, int page, int size) {
    SearchAndRetrievalParams params = SearchAndRetrievalParams.builder()
            .pageNumber(0)
            .pageSize(1000)  // ← loads 1000 records regardless of how many belong to this suite
            .build();

    PageResult<EntityWithMetadata<TestCaseDTO>> allTestCases =
            entityService.findAll(MODEL_SPEC, TestCaseDTO.class, params);  // ← full table scan

    List<TestCaseDTO> filtered = allTestCases.data().stream()
            .map(this::withId)
            .filter(tc -> suiteId.equals(tc.getSuiteId()))    // ← filtering in Java, not Cyoda
            .filter(tc -> !tc.isDeleted())
            .sorted(...)
            .skip((long) page * size)
            .limit(size)
            .toList();

    long total = allTestCases.data().stream()  // ← iterates the entire list a SECOND time just to count
            .map(this::withId)
            .filter(tc -> suiteId.equals(tc.getSuiteId()))
            .filter(tc -> !tc.isDeleted())
            .count();
    ...
}

Offending Code — SuiteService.java (same pattern)

public PageResult<SuiteDTO> getSuitesByProjectId(UUID projectId, int page, int size) {
    List<SuiteDTO> all = entityService.findAll(MODEL_SPEC, SuiteDTO.class)  // ← ALL suites, all projects
            .data().stream()
            .map(this::withId)
            .filter(s -> projectId.equals(s.getProjectId()))  // ← Java-level filter
            .sorted(...)
            .toList();
    ...
}

The same anti-pattern is repeated verbatim in TestRunService.getTestRunsByProjectId() and AttachmentService.getAttachmentsByCaseId().

Why the Fix Exists But Isn't Used

The EntityServiceImpl already exposes a search() method that accepts a GroupCondition and pushes filtering down to the Cyoda layer — meaning the data store only returns matching records. It is used for findByBusinessId() but never for the main list queries.

// ✅ SOLUTION: Use EntityService.search() to push the filter into Cyoda
public PageResult<TestCaseDTO> getTestCasesBySuiteId(UUID suiteId, int page, int size) {

    SimpleCondition suiteFilter = new SimpleCondition()
            .withJsonPath("$.suiteId")
            .withOperation(Operation.EQUALS)
            .withValue(objectMapper.valueToTree(suiteId.toString()));

    SimpleCondition notDeleted = new SimpleCondition()
            .withJsonPath("$.deleted")
            .withOperation(Operation.EQUALS)
            .withValue(objectMapper.valueToTree(false));

    GroupCondition condition = new GroupCondition()
            .withOperator(GroupCondition.Operator.AND)
            .withConditions(List.of(suiteFilter, notDeleted));

    SearchAndRetrievalParams params = SearchAndRetrievalParams.builder()
            .pageNumber(page).pageSize(size).build();

    // Cyoda returns ONLY matching records — no in-memory filtering needed
    PageResult<EntityWithMetadata<TestCaseDTO>> result =
            entityService.search(MODEL_SPEC, condition, TestCaseDTO.class, params);

    return toPage(result);
}

Performance Impact: With 10 suites × 50 cases each, every call to GET /cases currently deserializes 500 objects and throws away 490 of them. With 100 suites × 100 cases, that becomes 10,000 objects for every request. Pushing the filter into Cyoda means only the 50–100 relevant records cross the gRPC boundary.

2

N+1 Query Pattern in Reorder Operations

High  Backend

Affected files: TestCaseService.java → reorderTestCases(), SuiteService.java → reorderSuites()

When the user drag-and-drops to reorder suites or test cases, the frontend sends a PATCH request containing a list of {id, sortOrder} pairs. The backend then loops over each item and makes a separate round-trip to the Cyoda gRPC layer to fetch, update, and save each entity individually. For N items being reordered, this produces 2×N gRPC calls (one getById + one update per item).

// ❌ N+1 PROBLEM: 2 gRPC calls per item in the list
public void reorderTestCases(List<ReorderItemDTO> items) {
    for (ReorderItemDTO item : items) {
        getTestCaseById(item.id())   // ← gRPC call #1 per item: fetches full entity
            .ifPresent(tc -> {
                tc.setSortOrder(item.sortOrder());
                entityService.update(tc.getId(), tc, null);  // ← gRPC call #2 per item
            });
    }
}
// Reordering 20 cases = 40 gRPC calls. Each blocks a thread.

Recommended Fix

Use EntityService.save(Collection<T>) / EntityService.updateAll(Collection<T>) which already exists and supports batch operations. Fetch all entities in one call, apply the sort order changes in memory, then persist all at once.

// ✅ Batch approach: 2 gRPC calls total regardless of list size
public void reorderTestCases(List<ReorderItemDTO> items) {
    Map<UUID, Integer> sortOrderMap = items.stream()
            .collect(Collectors.toMap(ReorderItemDTO::id, ReorderItemDTO::sortOrder));

    // 1 search call — fetch all cases that need updating
    List<UUID> ids = new ArrayList<>(sortOrderMap.keySet());
    List<TestCaseDTO> toUpdate = ids.stream()
            .map(this::getTestCaseById)
            .flatMap(Optional::stream)
            .peek(tc -> tc.setSortOrder(sortOrderMap.get(tc.getId())))
            .toList();

    // 1 batch update call — persists everything at once
    entityService.updateAll(toUpdate, null);
}
3

Triple Round-Trip on Every Create & Update Operation

High  Backend

Affected file: EntityServiceImpl.java → create() and update()

Every mutation — creating a test case, updating a step status, completing a run — goes through three sequential gRPC round-trips before returning a response to the client. The sequence is:

Client HTTP POST/PUT ↓ [1] repository.save(entity) ← gRPC write ↓ [2] repository.getEntityChangesMetadata() ← gRPC metadata query (to find transactionId → timestamp) ↓ [3] repository.findById(id, timestamp) ← gRPC read at exact point-in-time ↓ Return response to client

This means the minimum latency of any mutation is latency(gRPC₁) + latency(gRPC₂) + latency(gRPC₃). If each call takes 50ms, every button click that saves data waits at least 150ms before the server can respond — before any network overhead on the HTTP side.

// EntityServiceImpl.java — create() simplified
public <T> EntityWithMetadata<T> create(T entity) {
    // Round-trip #1: persist
    EntityTransactionResponse response = repository.save(modelSpec, tree).join();
    UUID entityId = response.getTransactionInfo().getEntityIds().getFirst();
    UUID transactionId = response.getTransactionInfo().getTransactionId();

    // Round-trip #2: fetch change history to find this transaction's timestamp
    List<EntityChangeMeta> changes = getEntityChangesMetadata(entityId);  // ← extra gRPC call
    EntityChangeMeta changeMeta = changes.stream()
            .filter(meta -> transactionId.equals(meta.getTransactionId()))
            .findFirst().orElse(null);

    // Round-trip #3: reload entity at exact point-in-time
    return getById(entityId, modelSpec, entityClass, changeMeta.getTimeOfChange());
}

The intent is to return entity state as it existed at the moment of write, to avoid races with concurrent updates. However, the transaction response already contains the entity IDs; the data sent to the write call is the entity's new state; it can be reconstructed without a re-read.

⚠️ Trade-off Note The fromTransactionResponse() fallback already implements this optimisation and is used when the point-in-time lookup fails. The recommended fix is to make this the primary path for simple create/update operations, reserving the re-read only for entities whose state may be transformed by Cyoda workflows during the transition.
4

Frontend API Waterfall: Suite → Cases → Steps (Cascaded N+1)

High  Frontend

Affected files: Repository.tsx, RunExecution.tsx, ReportDetail.tsx

All three of the heaviest pages implement the same 2–3 level waterfall fetch pattern. The page cannot render meaningful content until the entire chain resolves, and each level is blocked by the previous one completing. In ReportDetail.tsx, the chain reaches three levels deep:

Page Mount ↓ GET /projects/{id}/suites (1 request, ~200ms) ↓ (blocks until suites resolve) GET /suites/{s1}/cases (N parallel, each ~200ms) GET /suites/{s2}/cases ...GET /suites/{sN}/cases ↓ (blocks until all cases resolve) GET /cases/{c1}/steps (N×M parallel, each ~200ms) GET /cases/{c2}/steps ...GET /cases/{cN×M}/steps ↓ Page renders usable content

With 10 suites each containing 20 cases, ReportDetail fires 1 + 10 + 200 = 211 API requests on page load before showing any analytics data. Even with parallel fetching via useQueries, the browser's per-domain connection pool (6–8 connections) becomes the bottleneck, queuing requests behind each other.

// ReportDetail.tsx — three-tier waterfall
// Tier 1: 1 request
const { data: suites = [] } = useSuites(projectId!);

// Tier 2: N requests (one per suite) — blocked until Tier 1 resolves
const casesQueries = useQueries({
    queries: suites.map((suite) => ({   // ← suites.length == 0 until Tier 1 finishes
        queryKey: keys.cases.all(projectId!, suite.id),
        queryFn:  () => testCasesApi.list(projectId!, suite.id),
        enabled:  !!projectId && suites.length > 0,
    })),
});

// Tier 3: N×M requests — blocked until ALL of Tier 2 resolves
const casePairs = suites.flatMap((suite, i) =>
    (casesQueries[i]?.data ?? []).map((c) => ({ suiteId: suite.id, caseId: c.id }))
);
const stepsQueries = useQueries({
    queries: casePairs.map(({ suiteId, caseId }) => ({  // ← casePairs empty until Tier 2 finishes
        queryKey: keys.steps.all(projectId!, suiteId, caseId),
        queryFn:  () => testStepsApi.list(projectId!, suiteId, caseId),
        enabled:  !!projectId && casePairs.length > 0,
    })),
});

Recommended Fix

Introduce a backend endpoint that returns nested data in a single call. The backend already has all the information — the issue is purely that the API was designed as separate resources with no aggregation endpoint.

// Proposed new endpoint: GET /projects/{id}/repository
// Returns the full tree in one response:
{
  "suites": [
    {
      "id": "...",
      "name": "Login Tests",
      "cases": [
        {
          "id": "...",
          "title": "...",
          "priority": "HIGH",
          "steps": [
            { "id": "...", "action": "...", "expectedResult": "..." }
          ]
        }
      ]
    }
  ]
}

For pages that don't need steps on initial load (like Repository), returning suites + cases without steps eliminates ~95% of the requests. Steps remain lazy-loaded only when a case is selected.

5

No DOM Virtualization on Large List Renderings

Medium  Frontend

Affected files: Repository.tsx, RunExecution.tsx, TestRuns.tsx

The Repository page renders the full suite/case tree and the Run Execution page renders all test cases in the left panel as plain DOM elements. There is no windowing or virtual scrolling. Every element, even those scrolled far out of view, remains in the DOM and is processed by the browser's layout engine on every state update.

In a project with 20 suites of 50 cases each, the Repository renders 1,020 DOM elements simultaneously. Any state change — typing in a search box, toggling a checkbox, clicking a case — triggers a full reconciliation pass across the entire tree, even though only one element changed.

// Repository.tsx — renders ALL suites and ALL their cases unconditionally
{localSuites.map((suite) => (
  <div key={suite.id}>
    /* Suite header */
    {expandedSuites.has(suite.id) && suite.cases.map((testCase) => (
      <div key={testCase.id}>
        /* Renders even if 500 pixels below the viewport */
        <CaseRow case={testCase} ... />
      </div>
    ))}
  </div>
))}

Recommended Fix

Use @tanstack/react-virtual (already compatible with TanStack Query) or react-window to render only the rows in the visible viewport. For the suite tree specifically, collapse-by-default reduces the initial DOM size substantially as a simpler short-term fix.

// Quick win: collapse suites by default (Repository.tsx already has this logic)
// Change the initial state from "all expanded" to "all collapsed"

// Current (expensive): expand all on first load
useEffect(() => {
  if (apiSuitesData.length > 0) {
    setExpandedSuites(new Set(apiSuitesData.map(s => s.id)));  // ← expands everything
  }
}, [apiSuitesData]);

// Improved: only expand the first suite, or none
useEffect(() => {
  if (apiSuitesData.length > 0) {
    setExpandedSuites(new Set([apiSuitesData[0]?.id].filter(Boolean)));  // ← just the first
  }
}, [apiSuitesData]);
6

Base64 File Content Embedded in Metadata Responses

Medium  Backend · Network

Affected file: AttachmentDTO.java, AttachmentService.java

The AttachmentDTO contains a content field that stores the base64-encoded raw file content as a fallback when the EdgeMessage system is unavailable. This field is part of the same DTO that is returned by the list endpoints (GET /attachments, GET /attachments/by-case/{id}).

// AttachmentDTO.java — content field is included in ALL responses
public class AttachmentDTO implements CyodaEntity {
    private String fileName;
    private String fileType;
    private long fileSize;
    private UUID messageId;
    private String content;  // ← base64 of the full file. Could be MBs per attachment.
}

When listing all attachments for a project, if even a few files were stored with the inline fallback, the API response could return megabytes of data for what is intended as a metadata-only listing. A 1MB image becomes ~1.37MB as base64, and 10 such attachments would send ~14MB in a single JSON response.

Recommended Fix

Create a separate AttachmentMetadataDTO (without the content field) for list endpoints. Reserve the full AttachmentDTO with content only for the dedicated download endpoint. Alternatively, annotate the field with @JsonIgnore on the list DTOs, or use a Jackson view (@JsonView) to selectively serialize it.

// Quick fix: exclude content from serialization in list responses
public class AttachmentDTO {
    ...
    @JsonIgnore  // Never expose raw content in metadata endpoints
    private String content;

    // Expose via a dedicated accessor only in the download endpoint
    @JsonIgnore
    public String getContentForDownload() { return content; }
}
7

staleTime: 0 Forces Unnecessary Network Refetches

Low  Frontend

Affected file: hooks/useApi.ts

The useTestRun and useTestRuns hooks override the global staleTime with 0 and set refetchOnWindowFocus: true. While intentional for keeping run status fresh, this means every navigation back to the runs list — or every time the user switches tabs and returns — triggers a fresh fetch even if data was loaded one second ago.

// useApi.ts
export function useTestRuns(projectId: string, page = 0) {
  return useQuery({
    queryKey: keys.runs.list(projectId, page),
    queryFn:  () => testRunsApi.list(projectId, page),
    staleTime: 0,                  // ← data is ALWAYS stale immediately
    refetchOnWindowFocus: true,    // ← every tab switch triggers a fetch
  });
}

A more balanced approach is a short staleTime (e.g., 30 seconds) combined with targeted invalidation when the user explicitly completes or updates a run. This eliminates redundant fetches while still showing fresh data when it matters.

// Balanced approach: short staleTime + explicit invalidation
export function useTestRuns(projectId: string, page = 0) {
  return useQuery({
    queryKey: keys.runs.list(projectId, page),
    queryFn:  () => testRunsApi.list(projectId, page),
    staleTime: 30_000,   // ← treat data as fresh for 30 seconds
    // refetchOnWindowFocus: false  ← rely on mutation invalidation instead
  });
}

// In useCompleteTestRun, useUpdateTestRun — explicitly invalidate after changes
onSuccess: (_data, { projectId, id }) => {
  qc.invalidateQueries({ queryKey: keys.runs.all(projectId) });  // ← already there ✓
}

3. Top 5 Root Causes Summary

The seven findings above cluster into five core root causes, ordered by the magnitude of their performance impact:

# Root Cause Layer Severity Scope
1 No server-side filtering — all queries are full-table scans with in-memory Java filtering. The EntityService.search() API exists but is not used. Backend Critical All 4 main entity types
2 Frontend API waterfall — the UI requests suites, then cases per suite, then steps per case in serial dependency chains, blocking render for the full chain latency. Frontend High Repository, RunExecution, ReportDetail
3 Triple gRPC round-trip per mutation — every create/update executes write → metadata fetch → point-in-time re-read sequentially, tripling the latency of any user action that saves data. Backend High All mutations (create, update)
4 No DOM virtualization — all list items are rendered to the DOM at once, causing expensive layout recalculations on every state update even in large projects. Frontend Medium Repository, RunExecution
5 Oversized API payloads — attachment metadata responses may include raw base64 file content, and query cache settings force redundant refetches on navigation. Both Medium Attachments page, TestRuns page

4. Prioritized Remediation Roadmap

The matrix below groups fixes by implementation effort (horizontal axis) and performance impact (vertical axis). Start with the top-left quadrant — high-impact, low-effort changes — and work clockwise.
🚀 Quick Wins — Do Now (1–3 days each)
  • Add @JsonIgnore to AttachmentDTO.content field in list endpoints to eliminate multi-MB payloads
  • Change staleTime: 0 to staleTime: 30_000 in useTestRuns and useTestRun to cut redundant refetches
  • Change Repository.tsx initial suite expansion to "first only" or "collapsed" — reduces initial DOM size by ~90% for large projects
  • Add @JsonProperty(access = WRITE_ONLY) annotations to any internal Cyoda ID fields that leak into API responses unnecessarily
📋 Schedule — High Value, Moderate Effort (1–2 sprints each)
  • Replace all entityService.findAll() + .filter() calls in TestCaseService, SuiteService, TestRunService, AttachmentService with entityService.search(GroupCondition)
  • Replace per-item loops in reorderTestCases() and reorderSuites() with batch entityService.updateAll()
  • Add a new GET /projects/{id}/repository endpoint that returns suites + cases in one response, eliminating the frontend waterfall for Repository and RunExecution pages
  • Add react-virtual or @tanstack/react-virtual windowing to the Repository case list and Run Execution case panel
🔭 Long-Term — Architectural Improvements (1–2 months each)
  • Evaluate whether EntityServiceImpl.create() / update() can skip the point-in-time re-read for entities without workflow transformations, using fromTransactionResponse() as the primary path
  • Design a GraphQL or BFF (Backend for Frontend) layer to allow the frontend to request exactly the data shape it needs, eliminating over-fetching and multiple round-trips in one query
  • Add response caching (Redis or in-process) for frequently-read, infrequently-changed data such as project and suite lists
  • Introduce server-sent events or WebSocket push for run execution status updates instead of polling on page mount
📊 Monitoring — Measure Before & After
  • Add OpenTelemetry tracing to the Spring Boot service to measure gRPC call durations per endpoint
  • Add React DevTools Profiler sessions to baseline render counts before and after virtualization changes
  • Use browser DevTools Network waterfall to confirm the API request count drops from ~200+ to ~1–3 on ReportDetail page load
  • Set up Lighthouse CI to track Time-to-Interactive (TTI) regressions per PR
